# Доступ Codex к Google Scholar и NotebookLM

## A. Что включено «из коробки»

Поиск кандидатов публикаций по API Crossref/OpenAlex (`scripts/discover_crossref.py`, `scripts/discover_openalex.py`) и локальный контроль ссылок (`scripts/validate_research.py`). Никакой внешний аккаунт не подключён автоматически. Эти операции требуют сетевого доступа, который может ограничиваться текущим sandbox Codex.

## B. Рекомендуемое браузерное подключение (необязательно)

Чтобы Codex **мог реально открыть веб-интерфейс NotebookLM** и (если разрешено) выполнять ограниченные действия в Google Scholar, можно добавить Chrome DevTools MCP — проект команды ChromeDevTools.

Потребуются Chrome, Node.js/npm и подходящий режим доступа Codex. Устанавливайте сервер только после проверки его кода, прав доступа и настроек безопасности:

```bash
codex mcp add chrome-devtools -- npx chrome-devtools-mcp@latest
codex mcp list
```

Источник команды: https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/client-configurations.md

**Важные условия:**
- Само подключение MCP **не авторизует** пользователя в Google и не даёт доступ к закрытым аккаунтам. Пользователь должен войти в Google в том браузерном контексте, к которому подключён MCP.
- Устанавливайте доступ только в доверенном окружении. Браузерный MCP потенциально может видеть вкладки, страницы и чувствительные сведения. Не храните пароли в репозитории.
- Не обходите CAPTCHA/robots.txt, не выполняйте массовый скрапинг Scholar. Официальный Google Scholar не предоставляет массовый доступ к данным. API Crossref/OpenAlex предпочтительнее для программного поиска.
- Проверяйте, что выбранный сервер действительно предоставил инструменты, а не только присутствует в `codex mcp list`. Запишите тест успешного открытия/чтения страницы в `tool_log.md`.

**Отключение:** используйте средства управления MCP вашей версии Codex; не допускайте работы с браузерным профилем, содержащим приватные вкладки, если их доступ не нужен.

## C. Google Scholar

1. Codex генерирует точные запросы и ссылки `https://scholar.google.com/scholar?q=...`.
2. Если допустим разрешённый интерактивный доступ — открывает выдачу, фиксирует конкретную статью, URL, дату, библиографическую информацию, число/фильтры результата.
3. DOI и фактические результаты подтверждаются отдельно: издатель, Crossref, полный текст.
4. Если интерактивный доступ блокируется, ставит `NEEDS_USER_ACTION` / `BLOCKED`, продолжает поиск по Crossref/OpenAlex без притворного посещения Google Scholar.

Справка Google Scholar, в том числе о запрете массового доступа: https://scholar.google.com/intl/en/scholar/help.html

## D. Google NotebookLM — два разных случая

**Обычный NotebookLM (пользовательская версия)**: работа через реальный браузер, авторизованный Google-аккаунт и загрузку пользователем разрешённых источников. В данном наборе **нет официального универсального API для потребительского NotebookLM**. Не следует считать случайный сторонний пакет официальным.

**NotebookLM Enterprise (Google Cloud)**: существует документированная Enterprise API для операций с источниками, но она требует настроенного проекта/разрешений. Это **не** автоматический API-доступ к личному notebooklm.google.com. Документация: https://docs.cloud.google.com/gemini/enterprise/notebooklm-enterprise/docs/api-notebooks-sources

Там, где доступна такая интеграция, настройте клиент согласно документации Google, проверьте права и не загружайте файлы без согласия.

При отсутствии UI/API создайте `notebooklm_import_manifest.md`: ручные шаги, реальный список файлов и запросы. Статус NotebookLM при этом `NEEDS_USER_ACTION`, не `DONE`.

## E. Маршрут при полном отсутствии интеграций

`вопрос пользователя → Crossref/OpenAlex, если есть сеть → страницы издателей и разрешённые локальные PDF → матрица доказательств → черновик → локальный аудит → пакет для Google Scholar и NotebookLM → саммари с честным перечнем незакрытых шагов`.

Это частично автоматизированная работа, **не** эквивалент реального взаимодействия с сервисами.
